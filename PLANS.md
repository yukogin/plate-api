## Работа с документацией

- AGENTS.md — постоянные правила, стек, команды и соглашения. Создать на этапе 1, команды записывать после их появления в проекте.
- docs/specs/*.md — требования и критерии готовности отдельных этапов.
- PLANS.md — порядок работы, статус и краткие сведения о выполнении.
- docs/adr/*.md — принятые архитектурные решения и их причины. Создавать вместе с соответствующим решением.
- README.md — фактическая инструкция запуска и использования. Дополнять после каждого этапа.

Требования к API определяет backend-api.md; схема и инфраструктура описаны в architecture-and-database.md, доступ — в authentication.md. Остальные документы ссылаются на эти источники, чтобы не копировать требования.

## Как запускать этап в Codex

Пример первого запроса:

> Прочитай AGENTS.md, если он существует, PLANS.md и docs/specs/architecture-and-database.md. Реализуй только этап 1. Учитывай общую модель продукта из docs/specs/backend-api.md. В конце обнови статус этапа, перечисли изменения, выполненные проверки и ограничения.

Для следующего этапа указать его номер и файл ТЗ. Завершать этап после выполнения его критериев; не переходить автоматически к следующему. Внешнее развёртывание выполняется только как отдельный этап 5 после выбора платформы.

## Завершение этапа

Обновить статус и кратко записать результат. Отделять выполненные проверки от запланированных; непроверенное поведение не объявлять работающим. При блокировке указать причину и следующий шаг.

Автоматические тесты добавлять и запускать по отдельному запросу пользователя. Для каждого этапа подготовить воспроизводимые команды ручной проверки. Сборку и проверку типов можно выполнять.

## Результат этапа 1

- Созданы `AGENTS.md`, `README.md`, ADR 0001, каркас NestJS, конфигурация, модули `prisma`, `health`, `auth` и `recipes` (последние два пока без маршрутов).
- Добавлены Prisma-схема и сохранённая миграция `Recipe`, `User`, `Role`, Docker Compose с постоянным volume, пример окружения и lock-файл npm.
- Выполнено: `npm run db:generate`, `npm run db:migrate` на пустом локальном PostgreSQL, проверка таблиц через `psql`, `npm run typecheck`, `npm run build`, `docker compose config --quiet`.
- Ручные HTTP-проверки: `GET /api/v1/health` вернул 200 при доступной базе и 503 при остановленном контейнере; `/api/docs` вернул 200. Контейнер после проверки снова запущен.
- `npm audit --omit=dev` после обновления транзитивных зависимостей: 0 уязвимостей. Автоматические тесты не добавлялись и не запускались согласно правилу плана.
- Ограничения на момент этапа 1: вход, seed администратора и CRUD рецептов ещё не были реализованы. Локальный Git-репозиторий и `origin` добавлены после этапа 1; первый коммит опубликован в `origin/main` позднее.

## Результат этапа 2

- Добавлены явный seed администратора, bcrypt-хеширование, login DTO и маршрут `POST /api/v1/auth/login`, JWT с HS256, `JwtAuthGuard`, `RolesGuard` и составной декоратор `AdminOnly` для этапа 3.
- Swagger дополнен login DTO, ответом и Bearer-схемой; обновлены `.env.example`, `README.md`, `AGENTS.md` и ADR 0002.
- Выполнено: `npm run typecheck`, `npm run build`, ручная миграция и seed в отдельной локальной базе. Повторный seed не создал дубликат и не изменил существующую запись. Временная база после проверки удалена; основная база `plate` не затронута.
- Ручные HTTP-проверки: вход с нормализуемым email вернул JWT и роль admin; неверный пароль и неизвестный email дали одинаковые 401; пустой пароль и неизвестное поле дали 400; Swagger JSON содержит login и Bearer-схему.
- Проверка доступа guard и роли через реальные маршруты записи остаётся на этапе 3: таких маршрутов пока нет. Автоматические тесты не добавлялись и не запускались согласно правилу плана.

## Результат этапа 3

- Реализованы публичные список и детали рецептов, защищённые `AdminOnly` создание, PATCH и физическое удаление. Добавлены DTO, слои Controller → Service → Repository, общий формат ошибок, Swagger и примеры curl в README.
- Ручные проверки на отдельной локальной базе: полный цикл 201 → 200 → 200 → 204, повторное удаление и отсутствие записи — 404; неверный UUID — 400. Список не содержит ингредиенты и шаги, детали содержат их.
- Проверены пагинация, пустой результат и страница за пределами списка; буквальный поиск по `%` и `_`, регистронезависимый поиск по названию и описанию; вторичная сортировка `id DESC` при одинаковом `updatedAt`.
- На POST, PATCH и DELETE проверены 401 без токена и 403 для роли user; неверный и истёкший JWT дали 401. После смены роли в базе уже выданный токен использовал новую роль.
- Проверены валидация пустых строк, массивов, чисел, URL, неизвестных полей, `null` в обязательных полях, пустого PATCH; PATCH сохранил отсутствующие поля, очистил nullable-поля и заменил массив. Конкурентное отсутствие записи при update/delete переведено из Prisma P2025 в 404.
- При недоступной базе health вернул 503, список и login — 500 с общим форматом ошибки без SQL и строки подключения. Swagger JSON проверен для маршрутов, DTO, query, nullable-полей, ответов и Bearer-доступа.
- Выполнены `npm run typecheck`, `npm run build`. Автоматические тесты не добавлялись и не запускались согласно правилу плана. Временная база и процессы ручной проверки удалены после завершения.
