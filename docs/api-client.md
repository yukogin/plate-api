# API «Рецепты»: контракт для клиентского приложения

Актуально для реализации этапов 1–3. Внешнего URL пока нет. При локальном запуске с настройками по умолчанию базовый адрес — `http://localhost:3000/api/v1`; порт задаётся через `PORT`. Интерактивная документация доступна по `http://localhost:3000/api/docs`.

Запросы с телом отправляются как JSON с `Content-Type: application/json`. Даты в ответах — строки ISO 8601 в UTC, например `2026-11-07T09:00:00.000Z`. `id` — UUID. Отсутствующие необязательные значения рецепта возвращаются как `null`.

Для браузерного клиента сервер должен разрешить его origin в `CORS_ORIGINS`; по умолчанию CORS выключен. Нативному iOS-клиенту CORS не требуется.

## Доступ и маршруты

| Метод | Путь от базового адреса | Доступ | Успешный статус |
| --- | --- | --- | --- |
| GET | `/health` | публичный | 200 |
| POST | `/auth/login` | публичный | 200 |
| GET | `/recipes` | публичный | 200 |
| GET | `/recipes/{id}` | публичный | 200 |
| POST | `/recipes` | `admin` | 201 |
| PATCH | `/recipes/{id}` | `admin` | 200 |
| DELETE | `/recipes/{id}` | `admin` | 204, без тела |

Для POST, PATCH и DELETE передавайте заголовок `Authorization: Bearer <accessToken>`. Чтение рецептов не требует токена. Учётные записи создаются администратором вне публичного API; регистрации и API управления пользователями нет.

## Вход

`POST /auth/login`

```json
{
  "email": "admin@example.com",
  "password": "your-password"
}
```

Email обрезается по краям и приводится к нижнему регистру перед поиском. Пароль передаётся без изменения регистра и обрезки пробелов. Неверный формат email, пустой пароль или неизвестные поля дают 400.

Ответ 200:

```json
{
  "accessToken": "<jwt>",
  "tokenType": "Bearer",
  "expiresIn": 86400,
  "user": {
    "id": "a970ca2a-4458-44a4-af49-fda1e4e2492d",
    "email": "admin@example.com",
    "role": "admin"
  }
}
```

`expiresIn` измеряется в секундах; значение по умолчанию — 86400 (один день), сервер может настроить другое. Роли: `admin`, `user`. Пароль и хеш никогда не возвращаются. После истечения токена нужен повторный вход: refresh token и logout с отзывом токена отсутствуют. На каждой защищённой операции сервер читает текущую роль пользователя из базы, поэтому изменение роли действует сразу.

Неизвестный email и неверный пароль дают одинаковый 401 с сообщением `Неверный email или пароль`.

## Форматы рецепта

**Краткий рецепт** в `GET /recipes`:

```json
{
  "id": "19d25f04-c9d9-4198-a97d-df767b0089da",
  "title": "Овсяные панкейки",
  "description": "Быстрый завтрак",
  "prepTimeMinutes": 15,
  "servings": 2,
  "imageUrl": null,
  "createdAt": "2026-11-07T09:00:00.000Z",
  "updatedAt": "2026-11-07T09:00:00.000Z"
}
```

**Полный рецепт** в `GET /recipes/{id}`, POST и PATCH содержит все поля краткого рецепта, а также упорядоченные массивы:

```json
{
  "id": "19d25f04-c9d9-4198-a97d-df767b0089da",
  "title": "Овсяные панкейки",
  "description": "Быстрый завтрак",
  "ingredients": ["2 яйца", "80 г овсяных хлопьев"],
  "steps": ["Смешать ингредиенты", "Обжарить на сковороде"],
  "prepTimeMinutes": 15,
  "servings": 2,
  "imageUrl": null,
  "createdAt": "2026-11-07T09:00:00.000Z",
  "updatedAt": "2026-11-07T09:00:00.000Z"
}
```

Клиенту стоит использовать отдельные модели для краткого и полного рецепта: список не возвращает `ingredients` и `steps`. `description`, `prepTimeMinutes`, `servings`, `imageUrl` могут быть `null`. Остальные поля полного рецепта присутствуют всегда.

## Список, поиск и пагинация

`GET /recipes?page=1&limit=20&search=панкейки`

| Параметр | Правило |
| --- | --- |
| `page` | Положительное целое; по умолчанию 1 |
| `limit` | Целое от 1 до 100; по умолчанию 20 |
| `search` | Строка до 200 символов после обрезки пробелов; пустая строка выключает фильтр |

Поиск выполняется по буквальной подстроке в `title` **или** `description` без учёта регистра. `%` и `_` считаются обычными символами; в URL кодируйте `%` как `%25`. Сортировка: `updatedAt` по убыванию, затем `id` по убыванию.

Ответ 200:

```json
{
  "items": [
    {
      "id": "19d25f04-c9d9-4198-a97d-df767b0089da",
      "title": "Овсяные панкейки",
      "description": "Быстрый завтрак",
      "prepTimeMinutes": 15,
      "servings": 2,
      "imageUrl": null,
      "createdAt": "2026-11-07T09:00:00.000Z",
      "updatedAt": "2026-11-07T09:00:00.000Z"
    }
  ],
  "page": 1,
  "limit": 20,
  "total": 1,
  "totalPages": 1
}
```

При отсутствии совпадений: `items: []`, `total: 0`, `totalPages: 0`. Страница за пределами списка возвращает 200 с пустым `items` и фактическими `total` и `totalPages`.

## Получение, создание, изменение и удаление

`GET /recipes/{id}` возвращает полный рецепт. Неверный формат UUID даёт 400; корректный, но отсутствующий UUID — 404.

`POST /recipes` требует `admin`, `title`, `ingredients` и `steps`:

```json
{
  "title": "Овсяные панкейки",
  "description": "Быстрый завтрак",
  "ingredients": ["2 яйца", "80 г овсяных хлопьев"],
  "steps": ["Смешать ингредиенты", "Обжарить на сковороде"],
  "prepTimeMinutes": 15,
  "servings": 2,
  "imageUrl": null
}
```

Успех — 201 и полный созданный рецепт. Если необязательное поле не передано, в ответе оно будет `null`. `id`, `createdAt`, `updatedAt` задаёт сервер; передавать их в теле нельзя.

`PATCH /recipes/{id}` требует `admin` и хотя бы одно изменяемое поле. Возвращает 200 и полный обновлённый рецепт. Отсутствующее поле сохраняет прежнее значение. `null` очищает только `description`, `prepTimeMinutes`, `servings`, `imageUrl`. `title`, `ingredients` и `steps` не принимают `null`. Переданный массив целиком заменяет прежний, порядок элементов сохраняется. Пустое тело `{}` даёт 400.

`DELETE /recipes/{id}` требует `admin`. Успех — 204 **без JSON и без тела**. Повторное удаление даёт 404.

### Ограничения полей при POST и PATCH

| Поле | Правило |
| --- | --- |
| `title` | Строка, после trim от 1 до 200 символов; обязательна при POST |
| `description` | Строка до 5000 символов, включая пустую, либо `null` |
| `ingredients` | Упорядоченный массив из 1–100 строк; каждая после trim от 1 до 500 символов; обязателен при POST |
| `steps` | Упорядоченный массив из 1–100 строк; каждая после trim от 1 до 5000 символов; обязателен при POST |
| `prepTimeMinutes` | Целое число от 1 до 10080 либо `null` |
| `servings` | Целое число от 1 до 100 либо `null` |
| `imageUrl` | HTTP(S) URL до 2048 символов либо `null`; файл через API не загружается |

Неизвестные поля отклоняются с 400. Клиент должен отправлять числа как JSON-числа, а не строки.

## Ошибки

Единый формат для всех маршрутов:

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": ["Описание ошибки"]
}
```

`message` всегда массив строк; точные тексты валидации могут меняться, поэтому клиенту лучше опираться на HTTP-статус и не разбирать английские сообщения по шаблону.

| Статус | Когда встречается |
| --- | --- |
| 400 | Неверный JSON/DTO, query, UUID, лишние поля или пустой PATCH |
| 401 | Нет действительного Bearer-токена на операции записи либо неверный email/пароль при входе |
| 403 | Пользователь с ролью `user` выполняет операцию записи |
| 404 | Рецепт с таким UUID отсутствует, включая повторное удаление |
| 500 | Внутренняя ошибка; детали базы и сервера в ответ не включаются |
| 503 | `GET /health`: база недоступна |

`GET /health` возвращает `{"status":"ok"}` при доступной базе. У клиента нет публичного маршрута регистрации, персональных рецептов, загрузки изображений, избранного и refresh token.

## Минимальный сценарий интеграции

1. Для каталога вызывайте `GET /recipes` без токена и храните `page`, `limit`, `total`, `totalPages` из ответа.
2. При открытии карточки вызывайте `GET /recipes/{id}` для получения ингредиентов и шагов.
3. Для административных экранов выполните `POST /auth/login`, сохраните `accessToken` в защищённом хранилище платформы и передавайте его только в `Authorization: Bearer ...`.
4. При 401 на операции записи предложите повторный вход; при 403 покажите отсутствие прав. Для DELETE при 204 не пытайтесь декодировать JSON.
