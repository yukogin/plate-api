# Этап 4. Ревью реализации

Статус: готово после этапов 1–3.
Зависимости: все предыдущие этапы.

## Цель

Оценить соответствие реализации ТЗ, найти ошибки поведения и риски доступа к данным. Результат этапа — конкретные замечания и подтверждённые проверки.

Это задача на ревью. Не менять код приложения автоматически: исправления выполняются отдельной задачей по результатам отчёта.

## Источники требований

- architecture-and-database.md — слои, данные, запуск.
- authentication.md — вход, JWT, роли, seed.
- backend-api.md — API-контракт, поля, валидация и ошибки.
- AGENTS.md — постоянные правила проекта.
- README.md — документированные команды.
- PLANS.md — заявленный статус выполнения.

## Что проверить

### Архитектура и запуск

- Ответственность Controller, Service и Repository.
- Совместимость зависимостей, lock-файл, версия Node.js.
- Генерация Prisma Client и миграции на отдельной пустой локальной базе.
- Конфигурация приложения и корректное завершение.
- Health, Swagger, Docker Compose и сохранение данных PostgreSQL.

### Модель и API

- Соответствие полей схеме и JSON-контракту.
- Фильтрация, буквальный поиск, стабильная сортировка, пагинация.
- Валидация UUID, строк, массивов, чисел и неизвестных полей.
- Семантика PATCH: отсутствие поля, null, пустой объект, замена массивов.
- Корректные 201, 204, 400, 404 и единый формат ошибок.
- Поведение при конкурентном удалении/изменении записи.

### Аутентификация

- Хеширование и отсутствие пароля/хеша в ответах и логах.
- Повторный seed не меняет учётную запись и не создаёт дубликаты.
- Проверка JWT: подпись, допустимый алгоритм, срок действия.
- Получение текущего пользователя и роли из базы.
- Одинаковая ошибка входа для неизвестного email и неверного пароля.
- Защита каждой операции записи: 401 без валидного токена, 403 для user.
- Отсутствие обхода защиты через альтернативные маршруты.
- Публичное чтение без JWT.

### Документация

- README-команды соответствуют проекту.
- Swagger отражает реальные DTO, ограничения, nullable-поля и доступ.
- .env.example не содержит реальных секретов.
- ADR объясняет фактически принятые решения.
- Статусы PLANS.md отражают выполненную работу.

## Порядок проверки

1. Выполнить статическое ревью кода и документации.
2. Запустить доступные сборку и проверку типов.
3. При доступной инфраструктуре проверить API вручную на изолированной локальной базе с временными данными.
4. Не выполнять разрушительные команды над существующими базами, не удалять volumes и не использовать production-данные.
5. Не добавлять и не запускать автоматические тесты без отдельного запроса пользователя.
6. Если проверка невозможна, указать причину и воспроизводимую команду для последующего запуска.

## Отчёт

Создать docs/reviews/backend-api-review.md и обновить PLANS.md.

Формат замечания:
- Приоритет: critical / high / medium / low.
- Файл и строка.
- Конкретная проблема и затронутое требование.
- Сценарий воспроизведения.
- Влияние на работу приложения.
- Предлагаемое исправление.

Сначала перечислить находки по серьёзности, затем выполненные проверки и ограничения проверки. Для каждого критерия приёмки указать: выполнен / не выполнен / не проверен. Отсутствие находок не заменяет перечень фактически выполненных проверок.

## Критерии завершения

1. Создан отчёт с проверяемыми замечаниями либо явно указано отсутствие найденных проблем.
2. Каждое замечание связано с кодом или конкретным нарушением контракта.
3. Отдельно перечислены выполненные и недоступные проверки.
4. Есть перечень оставшихся задач и рекомендуемый порядок исправлений.
5. PLANS.md обновлён; завершение ревью не объявляется готовностью продукта, если есть блокирующие проблемы.
