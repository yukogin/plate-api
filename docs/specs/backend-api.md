## Продукт и границы MVP

REST API для iOS-приложения «Рецепты»: небольшой общий каталог проверенных рецептов. Чтение публичное. Создавать, редактировать и удалять рецепты могут только администраторы.

Стек и схема заданы в architecture-and-database.md; вход и проверка ролей — в authentication.md.
Рецепты общие: персональные каталоги и привязка рецепта к владельцу не нужны.

В MVP не входят регистрация, управление пользователями, загрузка изображений, избранное, категории, теги, рейтинги, комментарии, локализация, refresh tokens и облачный деплой.

## Контракт данных

Полный рецепт содержит id, title, description, ingredients, steps, prepTimeMinutes, servings, imageUrl, createdAt, updatedAt.

Правила:
- title: строка после trim, 1–200 символов.
- description: строка до 5000 символов или null; пустая строка допустима.
- ingredients: от 1 до 100 строк; каждая после trim содержит 1–500 символов.
- steps: от 1 до 100 строк; каждая после trim содержит 1–5000 символов. Порядок сохраняется.
- prepTimeMinutes: целое число от 1 до 10080 или null.
- servings: целое число от 1 до 100 или null.
- imageUrl: URL с протоколом http или https, до 2048 символов, или null.
- id и даты формируются сервером; клиент не может их задавать.
- Неизвестные поля отклоняются.
- Ограничения выше — принятые значения для MVP; отражать их в DTO и Swagger.

## Маршруты

| Метод | Путь | Доступ | Успех |
| --- | --- | --- | --- |
| GET | /api/v1/recipes | Публичный | 200 |
| GET | /api/v1/recipes/:id | Публичный | 200 |
| POST | /api/v1/recipes | admin | 201 |
| PATCH | /api/v1/recipes/:id | admin | 200 |
| DELETE | /api/v1/recipes/:id | admin | 204 без тела |

Все параметры id валидировать как UUID: неверный формат даёт 400, корректный отсутствующий UUID — 404.

### GET /recipes

Параметры query:
- page: положительное целое, по умолчанию 1.
- limit: целое от 1 до 100, по умолчанию 20.
- search: необязательная строка до 200 символов; trim, пустая строка означает отсутствие фильтра.

Искать буквальную подстроку без учёта регистра по title ИЛИ description. Символы % и _ в пользовательской строке не должны неожиданно становиться wildcard-операторами.

Сортировать по updatedAt DESC, затем id DESC для стабильного порядка при совпадении дат.

Ответ:

```json
{
  "items": [
    {
      "id": "<uuid>",
      "title": "Овсяные панкейки",
      "description": "Быстрый завтрак",
      "prepTimeMinutes": 15,
      "servings": 2,
      "imageUrl": null,
      "createdAt": "2026-11-07T09:00:00.000Z",
      "updatedAt": "2026-11-07T09:00:00.000Z"
    }
  ],
  "page": 1,
  "limit": 20,
  "total": 1,
  "totalPages": 1
}
```

ingredients и steps возвращаются только в деталях, создании и обновлении.
Для пустого результата items = [], total = 0, totalPages = 0. Страница за пределами списка возвращает 200 с пустым items и фактическими total/totalPages.

### GET /recipes/:id

Возвращает полный рецепт. В необязательных полях без значения возвращается null.

### POST /recipes

Обязательны title, ingredients и steps. Необязательные поля при отсутствии сохраняются как null.

```json
{
  "title": "Овсяные панкейки",
  "description": "Быстрый завтрак",
  "ingredients": ["2 яйца", "80 г овсяных хлопьев", "1 банан"],
  "steps": ["Измельчить хлопья", "Смешать ингредиенты", "Обжарить на сковороде"],
  "prepTimeMinutes": 15,
  "servings": 2,
  "imageUrl": null
}
```

Возвращает полный созданный рецепт.

### PATCH /recipes/:id

- Разрешены только изменяемые поля рецепта.
- Отсутствующее поле не меняет сохранённое значение.
- null очищает только необязательное поле.
- title, ingredients и steps не принимают null.
- Массив заменяется целиком, порядок сохраняется.
- Пустой объект отклоняется с 400.
- Возвращает полный обновлённый рецепт.

### DELETE /recipes/:id

Физическое удаление. Успех — 204 без тела; повторное удаление — 404.

## Ошибки

Использовать единый формат:

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": ["title must not be empty"]
}
```

message всегда массив строк. Точные тексты валидации могут зависеть от class-validator; статус и структура стабильны.

- 400 — некорректные DTO, UUID или query.
- 401 — отсутствующий, неверный или истёкший токен на защищённой операции.
- 403 — роль user на операции записи.
- 404 — рецепт не найден.
- 500 — внутренняя ошибка без stack trace, SQL или секретов.

Привести существующие ответы login и health к общему формату ошибок, сохранив их HTTP-коды. Ошибки Prisma переводить в подходящие HTTP-ответы, включая отсутствие записи при update/delete.

## Критерии готовности

1. Без токена работают список и детали; поиск и пагинация соответствуют контракту.
2. Admin может выполнить полный цикл создать → прочитать → изменить → удалить.
3. User получает 403 на каждой операции записи.
4. Без валидного токена запись возвращает 401.
5. Валидация охватывает пустые строки, неизвестные поля, массивы, null, UUID и query.
6. PATCH различает отсутствие поля и null.
7. Отсутствующий рецепт возвращает 404; удаление — 204 без тела.
8. Проект собирается, Swagger и README соответствуют фактическому API.
