# Этап 2. Аутентификация и роли

Статус: готово после этапа 1.
Зависимость: [Архитектура и база данных](architecture-and-database.md).

## Цель

Добавить вход по email и паролю, выдачу JWT и переиспользуемую защиту операций для роли admin.

## Учётные записи

- Роли: admin и user.
- Публичной регистрации и API управления пользователями в MVP нет.
- Чтение рецептов будет публичным; обычному читателю не нужна учётная запись.
- Схема поддерживает роль user для существующих или созданных отдельно записей.

## Seed администратора

- Отдельная команда берёт ADMIN_EMAIL и ADMIN_PASSWORD из окружения.
- Email нормализуется через trim и lowercase.
- Пароль хешируется bcrypt или Argon2 с солью; выбранный подход и параметры документируются.
- При существующем email команда не изменяет пароль или роль автоматически. Сообщает, что запись уже существует, без вывода секретов.
- Повторный запуск не создаёт дубликаты.
- Отсутствующие или некорректные настройки приводят к понятной ошибке без вывода пароля.
- Не запускать seed автоматически при старте сервера.

## Вход

POST /api/v1/auth/login — публичный маршрут.

Запрос:

```json
{
  "email": "admin@example.com",
  "password": "example-password"
}
```

Email проверяется как email и нормализуется. Пароль не обрезается и не меняет регистр. Пустой пароль и неизвестные поля отклоняются с 400.

Успешный ответ — 200:

```json
{
  "accessToken": "<jwt>",
  "tokenType": "Bearer",
  "expiresIn": 86400,
  "user": {
    "id": "<uuid>",
    "email": "admin@example.com",
    "role": "admin"
  }
}
```

expiresIn — число секунд, соответствующее настройке JWT_EXPIRES_IN. Срок действия по умолчанию — 1 день. Формат конфигурации документировать.

Неверный пароль и отсутствующий email дают одинаковую ошибку 401 с сообщением «Неверный email или пароль». Не возвращать passwordHash.

## JWT и доступ

- Принимать токен только из Authorization: Bearer <token>.
- Проверять подпись, срок действия и допустимый алгоритм.
- Секрет задаётся через JWT_SECRET; не использовать встроенный запасной секрет.
- Payload содержит sub с UUID пользователя и временные claims. Пароль и его хеш в payload не включать.
- На защищённом запросе получать текущую запись пользователя по sub; при её отсутствии возвращать 401.
- Для проверки прав использовать текущую роль из базы, чтобы изменение роли применялось сразу.
- Добавить JWT guard и механизм проверки роли, например декоратор Roles и RolesGuard.
- Без токена, с неверным или истёкшим токеном — 401.
- Для аутентифицированного user на admin-маршруте — 403.
- Публичные маршруты чтения не должны требовать JWT.
- Refresh tokens, logout с отзывом токена и управление сессиями не входят в MVP. После истечения токена нужен повторный вход.

## Критерии готовности

1. Seed создаёт администратора со стойким хешем и безопасно выполняется повторно.
2. Администратор входит и получает JWT по описанному контракту.
3. Некорректные credentials возвращают одинаковый 401.
4. Готовы guard и проверка ролей для этапа 3.
5. Хеш пароля, пароль и JWT-секрет не попадают в ответы и логи.
6. Проект собирается, документация обновлена.

Проверку защиты реальных операций записи завершить на этапе 3. Подготовить ручные сценарии; автоматические тесты — по отдельному запросу.
