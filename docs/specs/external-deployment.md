# Этап 5. Внешнее развёртывание API

Статус: не начат.
Зависимость: [ревью реализации](implementation-review.md) и исправление его блокирующих замечаний.
Контракт API: [backend-api.md](backend-api.md).

## Цель и предварительное решение

Сделать API доступным клиентскому приложению по публичному HTTPS-адресу с постоянной PostgreSQL-базой. До начала реализации выбрать платформу, регион, домен и способ эксплуатации PostgreSQL; зафиксировать выбор и его последствия в ADR. Текущий локальный Docker Compose и `localhost` не являются внешним развёртыванием.

## Инфраструктура и доступ

- Приложение доступно только через HTTPS с действительным сертификатом; HTTP перенаправляется на HTTPS или закрыт. Публичный адрес содержит существующий префикс `/api/v1`.
- PostgreSQL имеет постоянное хранилище и не открыт для произвольных подключений из интернета. Доступ приложению и администраторам ограничен средствами выбранной платформы.
- Включить резервное копирование базы, определить срок хранения и документировать восстановление. Проверить восстановление на отдельной базе, не затрагивая рабочие данные.
- Передавать `DATABASE_URL`, `JWT_SECRET` и другие секреты через защищённые настройки платформы; не добавлять их в Git, образ, логи и публичную документацию. Для браузерных клиентов задать точные `CORS_ORIGINS`, если они нужны. `NODE_ENV=production`.
- Настроить перезапуск процесса, доступ к журналам и наблюдение за `GET /api/v1/health`: 200 при доступной базе и 503 при недоступной. Не включать параметры подключения в ответ health.

## Выпуск и изменения базы

- Воспроизводимо установить зависимости из lock-файла, сгенерировать Prisma Client и собрать приложение.
- Применять сохранённые миграции командой `npm run db:migrate` до переключения трафика на новую версию. Не использовать `prisma db push` или сброс базы. Перед изменениями схемы иметь актуальную резервную копию.
- Выполнять `npm run db:seed-admin` отдельно и только при необходимости; seed не должен менять существующую учётную запись. Пароль администратора не выводить и не хранить в артефактах выпуска.
- Описать порядок отката приложения и действий при несовместимой миграции. Откат кода не должен автоматически удалять данные или откатывать SQL вслепую.

## Документация и результат

- Записать выбранную платформу, домен, настройки выпуска, миграций, резервного копирования, восстановления и отката в README или отдельной эксплуатационной инструкции. Секреты указывать только по именам переменных.
- Обновить [документацию клиента](../api-client.md): заменить утверждение об отсутствии внешнего URL фактическим базовым адресом и описать клиентские ограничения, если они появятся.
- Обновить PLANS.md фактическими проверками и статусом. Не объявлять этап завершённым только по успешной сборке или запуску процесса.

## Критерии готовности

1. Выбор платформы и домена зафиксирован; API отвечает по HTTPS с корректным сертификатом.
2. Постоянная PostgreSQL-база доступна приложению, миграции применены без потери существующих данных; прямой публичный доступ к базе закрыт.
3. Секреты настроены вне репозитория и артефактов; проверены доступ администратора и отказ 401/403 без нужных прав.
4. На внешнем адресе проверены health, Swagger (в соответствии с выбранной политикой доступа), публичное чтение и полный цикл CRUD на временном рецепте. Проверочный рецепт удалён.
5. Резервное копирование включено; процедура восстановления проверена на отдельной базе и задокументирована.
6. Описаны перезапуск, наблюдение, выпуск новой версии и безопасный откат. README и клиентская документация содержат действующий адрес и воспроизводимые команды.

Проверки выполнять без удаления рабочих данных и volumes. Автоматические тесты — по отдельному запросу пользователя, согласно PLANS.md.
