# Ревью Backend API «Рецепты»

Дата: 2026-11-07. Область: локальная реализация этапов 1–3 по [плану](../../PLANS.md). Проверки выполнены на отдельной базе `plate_review_20261107`; код приложения не изменялся. Приоритеты ниже отражают риск перед [внешним развёртыванием](../specs/external-deployment.md).

## Замечания

### 1. Medium — время ответа раскрывает наличие учётной записи

- **Место:** [`src/auth/auth.service.ts:25–28`](../../src/auth/auth.service.ts).
- **Проблема и требование:** условие `!user || !await compare(...)` пропускает bcrypt для неизвестного email. Хотя текст 401 одинаков, это ослабляет требование одинаковой ошибки для неверных credentials из [ТЗ аутентификации](../specs/authentication.md).
- **Воспроизведение:** на изолированной базе отправить неверный пароль для существующего и неизвестного email. При ручном замере получено примерно 0,274 с и 0,006 с соответственно. Это один локальный замер, а не статистическая оценка удалённой атаки.
- **Влияние:** многократные запросы могут помочь определить зарегистрированные email.
- **Исправление:** выполнять bcrypt-сравнение с заранее подготовленным фиктивным хешем и для отсутствующего пользователя, затем возвращать тот же 401. Повторно измерить распределение времени ответа.

### 2. Medium — нет ограничения попыток входа

- **Место:** [`src/auth/auth.controller.ts:12–20`](../../src/auth/auth.controller.ts), [`src/auth/auth.service.ts:25–29`](../../src/auth/auth.service.ts).
- **Проблема и требование:** маршрут входа принимает повторные попытки без ограничения по частоте; в `src` и `package.json` механизм ограничения не найден. Это риск для публичного входа перед [этапом 5](../specs/external-deployment.md), а не нарушение отдельного численного лимита в текущем API-контракте.
- **Воспроизведение:** отправить `POST /api/v1/auth/login` с неверным паролем и получить 401; затем проверить код маршрута и конфигурацию: счётчик попыток и обработка лимита отсутствуют. Многократные запросы и нагрузочная проверка не проводились.
- **Влияние:** подбор пароля и расход CPU на bcrypt не ограничены приложением.
- **Исправление:** определить политику ограничения попыток и настроить её в приложении либо на входном шлюзе; учесть IP, учётную запись, прокси и ожидаемую нагрузку, затем проверить срабатывание и восстановление доступа.

### 3. Low — пример поиска из README возвращает 400

- **Место:** [`README.md:118`](../../README.md).
- **Проблема и требование:** пример `curl` содержит кириллицу в URL без кодирования, поэтому документированная команда не воспроизводит поиск. Критерий 8 [ТЗ API](../specs/backend-api.md) требует соответствия README фактическому API.
- **Воспроизведение:** выполнить команду из строки 118: получен HTTP 400 до обработки NestJS. Команда с `curl --get --data-urlencode 'search=панкейки'` возвращает 200.
- **Влияние:** разработчик клиента может принять рабочий поиск за сломанный маршрут.
- **Исправление:** заменить пример на `curl --get 'http://localhost:3000/api/v1/recipes?page=1&limit=20' --data-urlencode 'search=панкейки'`.

### 4. Low — часть ограничений DTO отсутствует в Swagger

- **Место:** [`src/recipes/recipe-response.dto.ts:41–51`](../../src/recipes/recipe-response.dto.ts), [`src/auth/login.dto.ts:15–18`](../../src/auth/login.dto.ts).
- **Проблема и требование:** Swagger JSON описывает `page`, `limit`, `total`, `totalPages` как `number`, хотя это целые значения; для непустого пароля не указан `minLength`. Критерий 8 [ТЗ API](../specs/backend-api.md) и [ревью](../specs/implementation-review.md) требуют точной документации DTO.
- **Воспроизведение:** открыть `/api/docs-json` и посмотреть схемы `RecipeListDto` и `LoginDto`; сравнить с runtime-валидацией и ответом.
- **Влияние:** клиент, сгенерированный по OpenAPI, не узнает часть ограничений.
- **Исправление:** явно задать `type: 'integer'` для счётчиков и `minLength: 1` для пароля; сверить всю схему с runtime-контрактом.

## Выполненные проверки

- Статически проверены слои Controller → Service → Repository, маршруты, Prisma-схема, DTO, guards, конфигурация, ADR, инструкции, `.env.example` и игнорирование `.env`. Настоящих секретов в отслеживаемых файлах не обнаружено; это не аудит всей истории Git.
- Node.js 24.18.0 и npm 11.16.0; `npm run db:generate`, `npm run typecheck`, `npm run build`, `docker compose config --quiet` завершились успешно. `npm audit --omit=dev` сообщил 0 известных уязвимостей на момент проверки.
- На пустой отдельной базе `npm run db:migrate` создал `Recipe`, `User`, `_prisma_migrations` и enum `Role`. Повторный seed администратора не создал дубликат и не заменил пароль. Хеш в базе имеет длину 60 символов; содержимое хеша и пароли в отчёт не включены.
- PostgreSQL-контейнер был healthy; Compose использует именованный volume. `GET /api/v1/health` вернул 200 при доступной базе и 503 при недоступной; `/api/docs` вернул 200. При недоступной базе список вернул 500 с общим сообщением без SQL и строки подключения.
- Вход администратора вернул 200, Bearer JWT и роль без хеша; неизвестный email и неверный пароль дали одинаковую форму 401. Истёкший JWT, JWT с неподходящим алгоритмом и токен для отсутствующего пользователя дали 401. Роль берётся из базы при каждом запросе: после временной смены роли пользователя уже выданный токен получил новые права; роль возвращена обратно.
- Публичное чтение, пустой список, список с пагинацией, поиск по буквальным `%` и `_`, детали, полный цикл admin CRUD, очистка nullable-поля и замена массива через PATCH проверены HTTP-запросами. Неверный UUID и некорректные DTO/query дали 400; отсутствующий рецепт — 404; DELETE — 204 без тела. Для POST, PATCH и DELETE без токена получен 401, с ролью user — 403.
- В одном конкурентном сценарии PATCH и DELETE одной записи DELETE вернул 204, PATCH — 404; ошибки 500 не было. В Swagger проверены маршруты, Bearer-доступ и nullable-поля.
- Временные процессы остановлены, база `plate_review_20261107` удалена; существующая база и Docker volume не удалялись.
