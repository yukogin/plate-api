# ADR 0002: локальные учётные записи и JWT

Статус: принято, 2026-11-07.

## Контекст

Чтение общего каталога будет публичным. Операции записи доступны администратору; публичная регистрация и управление пользователями не нужны. Роль должна применяться сразу после её изменения в базе.

## Решение

- Администратор создаётся отдельной идемпотентной командой. Email нормализуется перед поиском и сохранением. Пароль хранится как bcrypt-хеш с индивидуальной солью и cost factor 12.
- Публичный login выдаёт подписанный HS256 JWT с `sub`, `iat`, `exp`; срок задаётся `JWT_EXPIRES_IN`. Секрет обязателен и хранится вне репозитория.
- `JwtAuthGuard` принимает только `Authorization: Bearer <token>`, проверяет подпись, алгоритм и срок, затем загружает текущего пользователя из PostgreSQL. `RolesGuard` читает роль из загруженной записи. Декоратор `AdminOnly` объединяет оба guard для будущих маршрутов записи.

## Рассмотренные альтернативы

- Сессии с хранением на сервере требуют отдельного жизненного цикла сессий для iOS-клиента.
- Роль внутри JWT могла бы устареть до окончания его срока. Чтение роли из базы применяет её изменение сразу.
- Автоматическое создание администратора при старте усложнило бы контроль учётной записи и секретов; seed выполняется явно.

## Последствия

- Изменение роли или удаление пользователя применяется на следующем защищённом запросе.
- После истечения JWT нужен повторный login; refresh и отзыв токенов не реализуются в MVP.
- Проверка JWT и роли на реальных операциях записи выполняется на этапе 3.
